# R6 compatibility rollout and rollback

Owner accepted the neutral option design on 2026-10-01. Migration/backfill preparation is authorized; database execution and production deployment have not been authorized. No database target is currently confirmed.

## Model and admin operation

- `ProductVariant.id` remains the inventory and cart identity. `optionKey = default` is the explicit unlabeled no-choice option; named keys are `named:` plus NFKC-normalized, lowercase, whitespace-collapsed labels. Punctuation and Arabic characters are preserved. Labels are limited to 160 characters, keys to 200. Keys are unique per product, including inactive inventory.
- Product creation uses one nested write to create a default and its initial stock. `Product.stock` starts at zero and is no longer edited through the product form. Product pricing/discounts remain shared by all options.
- To make a selectable product, create with zero initial stock, add the first named choice and explicitly check “Deactivate the other displayed active options when saving.” Its request lists the displayed default ID. To return to simple, create/reactivate a default with that same explicit action listing the displayed active named/unmapped IDs. Deactivation and the target write share one transaction: a failed create/update rolls back deactivation. Stale/foreign IDs or newly active conflicting options reject the request rather than silently disabling unseen options. Standalone deactivation remains available and can leave a product temporarily unavailable. No stock transfer or cart-ID replacement occurs. An existing option cannot change between default and named identity.
- Null `optionKey` means unresolved legacy inventory. It is unavailable at product selection, cart read/update/add, and checkout. Existing cart rows stay intact and must be removed/reselected by the customer; inactive, deleted, foreign or variantless selections are also unavailable.
- Admin/R5 aggregates still sum **all active variant stock**, including unresolved legacy stock. Storefront catalog availability includes only mapped active options. This intentional temporary difference exposes inventory needing reconciliation without selling ambiguous choices. The R5 SQL, thresholds, ordering, counting and pagination are unchanged.
- New orders snapshot `selectedOptionLabel`. Historical readers prefer that snapshot and otherwise use old size/color snapshots; they never derive historical labels from current catalog rows. Legacy columns, prices, names and snapshots remain intact. Cancellation continues to use the recorded variant ID, or `Product.stock` for variantless legacy items, with the existing stock marker/status protection.

## Compatibility release sequence

1. Complete focused independent review, disposable rehearsal and required pre-merge checks. Preserve the reviewed **R6 compatibility artifact** (this implementation plus generated client) under an identifiable release/version, called **R6-C** here. R6-C must contain neutral readers/writers, legacy snapshot fallback and both cancellation paths. An actual release identifier must be recorded before deployment; none exists yet.
2. Obtain a separate production deployment/data decision and approved production execution procedure. The supplied config/runner deliberately support disposable targets only; do not bypass their guard for production. The production procedure must use the same reviewed mapping logic and verify the exact target, migration history, backup/restore and owner reconciliation.
3. During a maintenance window, pause catalog mutations and checkout, drain old application instances, then apply the atomic compatibility migration. It adds nullable columns, replaces the clothing uniqueness index with the neutral index, and installs a guard; it does not backfill data. Old columns remain. Never run old catalog writers after the old size/color index is removed.
4. Deploy R6-C before reopening traffic. Run the approved report/backfill under the catalog-write freeze, verify inventory/reference preservation and resolve owner-approved mappings. Keep unresolved rows unavailable; do not guess. Refresh clients so stale clothing-era pages cannot present ambiguous new choices. Verify affected flows, then lift maintenance. Keep R6-C available as the rollback baseline for subsequent releases.

## Rollback

- After neutral options or post-migration orders exist, **R6-C is the safe application rollback baseline**, subject to its acceptance passing. Pre-R6 `main` is not a safe rollback target: it does not understand neutral labels, default selection or new snapshots. Before R6-C has passed acceptance and been preserved, there is no established safe application rollback artifact; keep maintenance active and fix forward.
- Pause catalog mutations while rolling back a later application release to R6-C. Retain the expanded schema, neutral uniqueness/guard, every variant ID/stock/cart row and all order snapshots. Orders created after migration remain readable and cancellable; cancellations still restore the same variant even if it is inactive. Repeated cancellation must remain a no-op for stock.
- If the rollout itself fails after purchases have resumed, pause affected purchasing and fix forward on the compatibility code. Do not restore an old backup over new orders, delete default/named variants, revert snapshot columns, or recreate the old uniqueness constraint over neutral rows. Disable an affected option explicitly if needed while retaining its ID and stock. Existing cart selections must never silently become another option.
- Reversing the schema/backfill or returning to pre-R6 code requires a separately approved reconciliation/reverse migration that accounts for **all post-migration orders and cancellations**; it is not prepared or authorized here. Legacy variantless cancellation can add to `Product.stock`; that ledger remains outside sellable stock until an owner-approved reconciliation, preventing double counting.

Implementation uses [Prisma v6 nested/interactive transactions](https://www.prisma.io/docs/orm/v6/prisma-client/queries/transactions) and [PostgreSQL row locks](https://www.postgresql.org/docs/current/explicit-locking.html). Product writers take `FOR NO KEY UPDATE` so they serialize without blocking checkout's product foreign-key key-share locks. Actual database behavior remains pending rehearsal.
