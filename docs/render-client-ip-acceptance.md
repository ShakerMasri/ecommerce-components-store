# Render client-IP policy and staging acceptance

Updated: 2026-10-06. Local implementation; **hosted acceptance pending**. This file is a procedure, not authorization to deploy or probe a service.

## Evidence and trust boundary

- [Render's PocketBase guidance](https://render.com/articles/host-pocketbase-on-render) explicitly says its public web-service ingress passes through Cloudflare/load balancing and overwrites caller-supplied `CF-Connecting-IP`. It warns that leftmost XFF remains caller-controlled. This is a provider statement, not a header observation from DaraKit.
- [Render's uptime guidance](https://render.com/docs/uptime-best-practices) states that all inbound web-service requests traverse Cloudflare. [Web services](https://render.com/docs/web-services) documents public access through custom domains and `onrender.com`, and says the container's HTTP port is not directly publicly reachable. Applying the overwrite guarantee to both reported public hostnames follows these general web-service statements; neither hostname was probed here.
- [Private networking](https://render.com/docs/private-network) says Free web services cannot receive private-network requests. The owner reports this service is Free. A paid service's internal network can bypass Cloudflare; same-workspace callers would then be inside the trust boundary. Reassess this policy before enabling private ingress, changing hosting, adding intermediary Workers/proxies, or exposing another origin. The application cannot authenticate a proxy just from a header or Host.
- [Render's Cloudflare DNS guidance](https://render.com/docs/configure-cloudflare-dns) describes DNS-only custom records pointing at Render. The owner reports the root record is DNS-only. This does not remove Render's managed Cloudflare ingress. Actual service identity, current compute plan, DNS/domain mappings, `www`, and deployed revision remain uninspected.
- [Better Auth 1.6 options](https://better-auth.com/docs/1.6/reference/options) supports `advanced.ipAddress.ipAddressHeaders`. Installed Better Auth and its nested core are **1.6.33**, matching the lockfile. Inspected core `utils/ip` and HTTP rate-limiter source: default XFF; single validated address without proxy ranges; IPv4-mapped conversion; IPv6 `/64`; production missing-IP key `no-trusted-ip|<path>`. Built-in quotas/storage are unchanged. Its plugin `onRequest` hooks execute after rate limiting, so a plugin cannot perform the required validation first.

## Implemented behavior

`src/lib/client-ip.ts` provides the one policy: production reads only `CF-Connecting-IP`, strictly accepts one IPv4/IPv6 literal, rejects lists (including duplicate headers or dangling commas), ports, zones, CIDRs, and malformed values, converts mapped IPv4 to IPv4, and canonicalizes IPv6 to its `/64`. Keeping Better Auth's existing `/64` also prevents anonymous application quota evasion by rotating IPv6 suffixes.

The auth configuration selects only that header and explicitly retains `/64`. The supported Next.js Request-handler adapter prepares the header before Better Auth's limiter: normalize valid values, remove invalid values, preserve body/cookies/origin/method/URL. This also handles Better Auth's more permissive filtering of empty comma tokens. No proxy ranges, fallback forwarding headers, or origin-check changes are introduced.

Missing/invalid production information uses a bounded shared fallback: application `ip:no-trusted-ip`, Better Auth `no-trusted-ip|<path>`. Neither consumer disables limits or invents per-request identities. Better Auth's existing warning can legitimately remain for such requests. Development/test ignores supplied IP headers and uses `127.0.0.1`; development without Redis retains its existing behavior. A local production `next start` needs the same trusted ingress contract and otherwise shares the missing-IP bucket.

Authenticated application keys remain `user:<server-supplied identifier>`, including existing verification-email recipient keys. Quotas, Redis timeout/error behavior, public-read outage behavior, TLS, CSRF/origin checks, authorization, prices, inventory, cart coordination, and checkout idempotency are preserved.

The caller trace is explicit: auth HTTP GET and POST both reach `auth.handler(withTrustedClientIp(request))`; POST first consumes the application auth bucket, plus the existing IP/recipient buckets for verification resends. Anonymous product reads use the same application resolver. Customer/admin mutations still derive their identifiers from authenticated server sessions. The only direct server-side auth API caller is `src/server/auth/index.ts` (`betterAuth.api.getSession`). Installed `to-auth-endpoints`/`dispatch` bypass the HTTP router's limiter on direct calls, as [Better Auth documents](https://better-auth.com/docs/concepts/rate-limit). That existing session read/refresh is not a sign-in, signup or email mutation entry point and does not resolve a new IP; it needs no Request adapter. Any future direct auth mutation would need its own protection review.

Installed core `getIp` reads only the configured header array; no alternate forwarding or caller-supplied internal identity header takes precedence. Request reconstruction retains method, URL/query, headers (including cookies/origin/content type) and body; the route has not consumed that body, and verification parsing uses a clone. Invalid header removal therefore reaches the built-in limited fallback rather than its permissive comma-token parser. Better Auth session creation also receives the prepared IP (IPv6 remains a `/64`), not an unvalidated alternate header.

### Timing, requests and expected results

Maximum **48 cookie-free POSTs**, two rounds of exactly 24 on a passing run, to `/api/auth/sign-in/email`, body `{}`, `Content-Type: application/json`, and the configured `APP_URL` as `Origin`. Use no credentials, cookies, redirects, automatic retries or extra warm-up/recovery requests. `{}` fails the installed endpoint's required email/password schema before database lookup/session creation/email callbacks. Stop on any other behavior; never substitute a real login payload.

Before each round, leave both identities' application auth buckets idle for **at least 20 minutes 5 seconds after their last attempt**, also past all returned resets. Installed Upstash 2.0.8 uses two weighted ten-minute slices and counter TTL `2 * window + 1000 ms`; a returned reset is only the next slice boundary, not assurance of an empty quota. This matches the documented [sliding-window approximation](https://upstash.com/docs/redis/sdks/ratelimit-ts/algorithms). Start each round about 30 seconds after a UTC ten-minute boundary and finish within three minutes, wholly inside that slice. Record request/response times and response Date/reset values to detect clock/boundary uncertainty. No key deletion, expiry manipulation, quota changes or manual restart.

Round 1: H1 = `darakit.com`, H2 = `darakit-staging.onrender.com`. Round 2 reverses H1/H2 after the idle requirement. All requests are sequential except coordination between the two clients; B must be ready for the short built-in window.

For A6–A20 use 15 preassigned cases: two distinct valid IPv4 claims; valid IPv6; IPv4-mapped IPv6; B's IP; malformed CF; comma-separated CF; trailing-comma CF; leading-comma CF; empty CF; duplicate CF in **two actual header lines**; and four cases with CF omitted and respectively XFF, X-Real-IP, Forwarded or True-Client-IP forged. Rotate the other forwarding values alongside the CF cases. Use documentation-range addresses for invented claims. Record labels rather than raw client IPs in the shareable report. Edge rejection of a malformed case is inconclusive for the expected application count; stop, do not replace it or add calls.

The order explicitly resolves masking: Better Auth's request-phase limiter is observed at A4/B1/A5 before application exhaustion; its rejections still count toward application's 20. A21/A22 are returned **before Better Auth**, so they prove only the application limiter. A6–A20 exercise aggregate application spoof resistance; a permitted 400 after the built-in window changes is **not** independent proof for that individual Better Auth spoof variant. Reversing the hosts gives each limiter a required spoof/isolation observation on both public paths without changing either quota, adding an endpoint, or disabling a protection.

Round 2's initial 400s demonstrate application recovery after round 1. After round 2, allow the same 20-minute-5-second idle period before normal use; no extra recovery probe fits this cap. Render Free may sleep between rounds; that does not clear Redis and must not be presented as Better Auth's natural recovery (A5 supplies that evidence within each round). Cold-start/transport delays, process replacement during a round, contamination, or crossing a time boundary can make the result inconclusive. Stop at the first unexpected result, side effect, target uncertainty or timing/cap violation; do not automatically rerun or increase the budget.

### Side effects and evidence

The passing run makes **48 application auth limiter decisions** (A: 44, B: 4), up to **44 Better Auth limiter decisions** (the four application denials never dispatch), and **zero intended application database reads/writes, account/session changes, emails or orders**. Better Auth's unchanged limiter uses process memory, not Redis/database storage. Application counters/analytics use the confirmed staging Redis and existing prefix. SDK retries, script loads and analytics mean 48 HTTP probes are not a 48-Redis-request budget.

Counter keys expire naturally; analytics contain client identifiers, and installed `@upstash/core-analytics` ingestion uses `ZINCRBY` with **no automatic TTL**. Those records may persist in existing hourly analytics keys. Owner acceptance of that limited staging data is required; this plan does not scan/delete shared keys or change retention. The application does not await all analytics work, so analytics alone are not a reliable pass/fail oracle. Database/email absence is supported by the reviewed invalid-body path and available existing sanitized telemetry, not by an unauthorized database query or by silence in logs alone.

Retain exact service/deploy/source and Redis target records, hostname mappings, UTC send/receive times, client labels, spoof labels, statuses, validation error classification and limiter-specific response headers in a private report. Exclude cookies, secrets, raw IPs and private logs from Git. Compare both clients and both rounds. Warning disappearance alone cannot prove resolution. Existing Redis outage/recovery evidence is reused separately; this procedure does not inject outages or establish durable cross-instance Better Auth storage.
