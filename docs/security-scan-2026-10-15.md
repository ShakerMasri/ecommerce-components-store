### 1. P2 — Production SMTP does not require encryption on STARTTLS ports

**Location:** `src/server/email.ts:173–188`, shared by auth mail and checkout receipts/notifications.

The transport sets `secure` only for port 465 and never sets `requireTLS`. On ports such as 587 or 2525, a server response without STARTTLS permits plaintext authentication and delivery. An attacker able to intercept the SMTP connection can strip the advertised capability or impersonate the plaintext server, exposing SMTP credentials and potentially verification/reset links and customer messages. Ordinary successful delivery to a TLS-capable provider does not test this failure mode. Port 465 uses implicit TLS and is outside this finding.

**Reproduction:** captured the options from the real `sendAuthEmail` function with synthetic production settings, then passed those options to installed Nodemailer 10.0.12 using an in-memory Duplex advertising `AUTH PLAIN` without STARTTLS. Authentication succeeded with `connection.secure === false`; no network connection or real credentials were used. The provider and a real network downgrade were not tested. Nodemailer's [SMTP documentation](https://nodemailer.com/smtp) confirms that `requireTLS` defaults to false and must be enabled to require an upgrade.

**Implemented 2026-10-16:** the shared SMTP options require STARTTLS whenever `NODE_ENV=production` and the port is not 465. Both ordinary auth mail and the bounded checkout adapter consume those options. Port 465 retains implicit TLS; development/test SMTP can deliberately remain plaintext. No certificate-verification bypass or insecure fallback was added.

**PASS — durable regressions:** `src/server/email-tls.test.ts` runs the real Nodemailer 10.0.12 ordinary and checkout transport paths over connected memory streams and real Node TLS, trusting only a public test fixture certificate. Successful delivery proves verified TLS before AUTH, envelope and DATA; absent capability, refused STARTTLS, malformed TLS and untrusted certificates reject before credentials/message transfer. Policy cases cover ports 25/587/2525/1025/465. Existing email/receipt/cancellation tests retain sender, MIME, sanitization, budget and implicit-TLS lifecycle coverage; deliberate plaintext receipt fixtures now explicitly use test mode. This is offline protocol evidence, not provider/inbox acceptance.

### 4. P2 — Concurrent partial product edits can violate the discount invariant

**Location:** `src/app/api/admin/products/[id]/route.ts:206–253`; consumed by `src/server/pricing.ts:8–9`.

The handler reads the existing price pair, validates the proposed combination, and later writes only the supplied fields without a lock or conditional update. Starting at regular price 100 / discount 40, simultaneous PATCH requests `{price: 50}` and `{discountPrice: 90}` can both validate against the old pair and return 200, leaving regular price 50 / discount 90. Checkout selects the non-null discount and can charge 90. The current migrations contain no database check for this pair. This requires overlapping authorized partial updates; it is not unauthenticated price manipulation.

**Reproduction:** scheduled both actual PATCH handlers to finish their stubbed reads before either write. Both returned 200 and persisted the invalid pair in the stub; a subsequent equivalent sequential request returned 400. Prisma Decimal and input/CSRF validation were real. This establishes the handler race, not a live PostgreSQL concurrency result.

**Correction:** serialize the read/validation/write for this product using an appropriate existing transaction/locking pattern, or use an optimistic conditional write that rejects stale state. A database constraint would be additional defense but requires separately authorized migration work.

**Implemented / offline PASS — Session 2, 2026-10-16:** price-changing PATCH requests read the pair with parameterized `SELECT … FOR NO KEY UPDATE`, validate the resulting Decimal pair and write through the same interactive Prisma transaction. This matches the existing option-writer row lock and allows checkout's product foreign-key key-share lock. A second price writer waits and then validates the committed pair; rejected requests write nothing. Non-price partial edits retain their existing fields; authorization, CSRF, rate limits and error responses remain. Checkout continues to obtain its effective price from server-owned product data. No migration, schema constraint or checkout-pricing change.

**Durable regressions:** `src/app/api/admin/products/[id]/route.test.ts` runs the real PATCH with real validation/Decimal/CSRF and a transaction-scoped row-lock model. Both controlled interleavings of price 100 / discount 40 → partial price 50 and discount 90 produce one 200 / one 400, never an invalid pair; tests assert the actual SQL, parameter binding, transaction-local write, null clearing, equal-price rejection, 0 rejection / 0.01 acceptance, metadata-only edits, missing product, transaction failure and protection rejections. Focused handler/option-mutation/actual-checkout suites: **92 passed / zero failures / zero skips**; `session2-price-results.json`. The scheduler models database locks; it does **not** establish real PostgreSQL behavior. [Prepared target and acceptance](#session-2-disposable-postgresql-acceptance--prepared-not-executed) remain approval-gated.

**Pattern verification:** installed Prisma/client 6.19.3 supports [interactive transaction callbacks](https://www.prisma.io/docs/orm/v6/prisma-client/queries/transactions); PostgreSQL documents [row-lock exclusion and waiting](https://www.postgresql.org/docs/15/explicit-locking.html#LOCKING-ROWS). ### 5. P2 — A pending catalog append can contaminate a newly selected category

**Location:** `src/components/products/ProductListingClient.tsx:88–128`, `:159–168`, `:332–335`.

Effect-triggered replacement requests get an abort signal, but Load more starts an append request without one. If a customer starts loading page 2 and changes category before it finishes, the new category can load first; the old request then appends unrelated products and overwrites pagination for the new category. The same stale-result issue applies to replacement requests started directly by the search handler without a signal.

**Reproduction:** rendered the actual listing component with deferred synthetic fetch responses and a simple category-control stub. After the new sensors result rendered, releasing the old unfiltered page-2 response displayed both the sensor and the unrelated old-category product. No browser or live catalog request was made.

**Correction:** cancel all obsolete requests and associate every result with the active filter/request generation before committing products, pagination or loading state. Cover filter changes during both append and manually triggered replacement requests.

**Implemented / offline PASS — Session 2, 2026-10-16:** every effect, append and manual replacement request owns an AbortController. Starting a new request cancels the previous one; category/search/reset handlers invalidate it before changing filters, and effect cleanup/unmount cancels any active request. Controller identity plus its abort status guard success, HTTP/network errors and `finally` before any catalog state changes. New requests explicitly select the appropriate loading mode, so an obsolete append cannot leave replacement loading stuck. Current pagination, category controls, empty/error recovery, EN/AR copy and accessibility markup are retained.

**Durable regressions:** actual `ProductListingClient` with real category controls/cards and deferred synthetic fetches covers EN/AR × append/manual replacement × category/search changes × obsolete success/HTTP failure/network failure × before/after replacement. Mocks deliberately ignore cancellation so identity guards must work. Tests check product isolation, preserved category controls, next-page 7, current replacement/append loading, active error preservation and recovery, and unmount during manual JSON parsing. Listing/card suites: **68 passed / zero failures / zero skips**; `session2-catalog-results.json`. This is jsdom component integration with mocked fetch, not a browser/hosted/live catalog test.
